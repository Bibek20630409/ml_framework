The pipeline, as it actually runs

Every command in the repo, in the order you'd actually type them — stage 0 from a clean clone through stage 15 in production. Two things to hold onto: this is not one straight line (a training path and an inference path that meet only at the model bundle), and the later stages fire on their own triggers, not because the stage above finished. Data that has to be decoded takes one extra fork at stage 5b.

Every block is followed by a what actually runs table: the command on the left, the repo file that executes it on the right, with the line number of the entry point where one exists. Paths are repo-relative; file:line pairs point at the function the command lands in.

Where exit 0 is not proof, a second table — what a healthy result looks like — says what to read and what the answer should be, and a symptom → cause → command table says where to go when it isn't. Both exist because of the rule this page is built on: every claim here is a state you have to observe, not one the command prints. Most commands below can fail while exiting 0 — a model that lost to its own baseline, a corpus that dropped a tenth of its samples, an ONNX graph missing its preprocessor, an Airflow task that cannot turn red. Each of those is named at the stage it happens in.

shared

One Dockerfile, five stages — but they are a dependency graph, not a sequence. src and base are shared intermediates, built once and cached and never named on the command line. The three real targets are independent siblings: building one never builds another, and none of them has to exist before the others.

order
Listed train-first to match this page, not the Dockerfile — where serve is written above train so the two serving variants sit together. Neither order means anything at build time. The one place it does matter is a bare docker build with no --target, which takes whichever stage is last.

note

engines
Which engine parses the data is a per-run choice, not a property of the file — --data-backend local | polars | spark, defined on three parsers with three different defaults: spark_preprocess defaults to spark, contracts to local, and mlf train / tune / select take it as a config override that falls through to data.backend (local). It keeps its name because DVC, the DAG and CI reference the path, and it keeps the spark default for the same reason: changing it would quietly change what the pipeline does. make benchmark times pandas against polars over a full build_bundle — 2.8–3.7× to polars, which is why the flag is worth reaching for on the training side too.

Stage 5b

Materialize a media corpus (audio · video · images · token shards)

training

Tabular data skips this entirely. For anything that has to be decoded, one offline pass walks the corpus, decode-probes every sample, and writes a shard index — the sample list, the labels, and a digest per sample. It is never implicit: mlf train refuses a media corpus that has not been through it, and names this command.

mlf materialize --data ./clips/train        # walk, decode-probe, write the index
mlf materialize --data ./clips/train --force    # rebuild an index that already exists

mlf materialize --data ./clips --sample-rate 0.05   # probe 5% for a quick smoke check
mlf materialize -c configs/audio.yaml --decoder audio.flac \
                --max-fault-rate 0.02               # exits 1 above the ceiling

# the walk covers read→demux→decode. This runs the other four stages too, once:
mlf materialize -c configs/audio.yaml --probe-full   # needs a config — see below

# writes, beside the data — a property of the CORPUS, not of a run:
./clips/train/_mlf_shards/
  shards.json      ← the manifest. n_samples lives here, and nowhere else
  entries.jsonl    ← one line per sample: shard, offset, nbytes, label, digest
  faults.jsonl     ← what could not be decoded. Empty on a clean corpus, never absent

# --- what tells you it worked -------------------------------------------
cat ./clips/train/_mlf_shards/shards.json            # n_samples lives here
wc -l ./clips/train/_mlf_shards/entries.jsonl        # must EQUAL n_samples
wc -l ./clips/train/_mlf_shards/faults.jsonl         # 0 on a clean corpus

seven stages
Storage → a tensor the model consumes is seven named stages, and this pass walks three of them. The split is not pedantry: each name marks a place where the cost, the device, or the thing that can go wrong is genuinely different. mlf decoders --show renders the head; the tail is declared by the preprocessor, because nothing about it belongs to a codec.
stagewhat it isruns where
reada positioned read — bytes, from wherever they liveworker
demuxcontainer → packets. Real for MP3/MP4, degenerate for a JPEGworker
decodereverse a compression schemeworker
constructattach a dtype, a shape and strides to a pointercollate
transformdtype/layout/scale — the mel matmul, the THWC→CTHW permutecollate or device
h2dhost → device. Async only from a page-locked buffertrainer
gpu_transformthe same transform, run after the copydevice
A pre-tokenized .bin shard has neither demux nor decode — a memmap slice is a page fault, not a call. A device decoder has decode and then no tail at all: no construct, no pinned buffer, no copy.
commands
Which verb runs which stages — and the answer is never the file name, always data.kind. A tabular run executes none of the seven whatever the verb: a table is payload="arrays", one tensor built at setup(), no decoder and no collate. The seven are the staged path — audio, video, token shards.

mlf train -c cfg.yamlall seven, per batch, every epoch
mlf tune · mlf hpo · mlf selectas train — they fit models
mlf lrread…transform plus h2d; never gpu_transform
mlf serve (audio/video)none — /predict returns 501, see stage 10
mlf decoders · models · init · export · dockerfilenone — they describe the framework, they do not read data
mlf lr is the odd row, and the reason a device_transform switch exists at all: torch_lr_finder drives the loader itself, so Lightning never fires the post-copy hook and a deferred transform would simply never run. It is turned off for that one caller rather than hoped about.
probe-full
The last four stages are per batch, so a per-sample decode probe cannot reach them — and a corpus can walk clean here and still die on step 1: ragged clips that will not stack, a filterbank geometry that does not divide the clip, a "device-agnostic" transform that is not. --probe-full pushes one batch of cleanly-decoded samples through construct → transform → h2d → gpu_transform, reusing the buffers the walk already decoded, and checks the device transform against the host one rather than taking the declaration's word. It needs --config, and that is not an oversight: which preprocessor owns the tail is a property of the run's data kind, not of the bytes on disk — and for video it is also where the clip geometry comes from, so the probe decodes the clips the run will actually read rather than whole files.
tolerance
The host-vs-device agreement threshold is an estimate, not a measurement. It was chosen on a CPU-only machine, where the device path is a no-op copy and the observed drift is exactly 0 — so a gpu_transform failure on your first real GPU run may be the threshold rather than your corpus. Calibrate it once: run this, read the host vs device max abs diff line the report prints, and set DEVICE_AGREEMENT_TOLERANCE an order of magnitude above it. The risk until then is one-sided and mild — too tight fails a healthy corpus loudly, rather than passing a skewed one in silence.
why
Two failure modes are invisible at training time by construction. An MP3 resyncs past damage and returns shorter audio with no error; a damaged H.264 stream emits artifacted frames while libavcodec merely logs. Both produce correctly-shaped tensors, so no handler in the training loop will ever run — they do not crash anything, they quietly make the model worse. This pass is the only place they can be caught: it compares decoded duration against the frame count, decoded frames against the container's declared count, and a device decoder against a host oracle.
ceiling
This is the only place the fault ceiling raises, and the reason is structural. At training time under DDP the same check would be a content-dependent abort — rank 0 could trip it while rank 1 does not, one rank stops, the rest block on the next collective, and the run hangs with no error message. Here there is one process and no collective, so failing is safe, deterministic and early. At runtime the rate is counted, logged and reported — never raised.
note
A sample that fails to decode still gets an index entry. The index declares what should exist, not what happens to decode today — dropping it would shrink n_samples, which is the one number every rank derives its batch count from. Labels come from the class directories (sorted, so the order is stable across machines), which is what makes fold planning a JSON scan rather than a decode pass over the whole corpus.

Stage 7

Model selection (optional)

training

mlf train tunes one model. mlf select compares model families — tuning each on its own space, cross-validating it, and measuring the four things a score does not tell you: latency, size, explainability and stability.

# bake off every compatible family, 4 at a time, disqualifying anything slower than 20 ms
mlf select --config configs/example_selection.yaml --max-latency-ms 20 --max-workers 4

mlf train  --config configs/example_selection.yaml --select   # compare, then train the winner

# the decision, written down — THIS is what stage 12 consumes
mlf select --config configs/example_selection.yaml --emit-config configs/winner.yaml

# the same run split across machines — two halves of one decision, not two commands:
# fan-out — evaluate ONE family, write its report, decide nothing
mlf select -c configs/example_selection.yaml --candidate xgboost --report-dir outputs/reports
# fan-in  — read every report in that dir, apply the constraints, name the winner
mlf select -c configs/example_selection.yaml --collect outputs/reports

note
The precedence chain is plugin defaults < synthesis < YAML < --set < explicit flags, so --data and --config compose rather than being alternatives. An uninstalled family is a refusal with the pip command, never a silent substitution.
corrupt
There is no --on-corrupt skip, and that is not an omission. Under DDP every rank must produce an identical number of batches or the next collective hangs with no error message, and continue is the one response that cannot preserve that. So a bad sample is substituted — a different index from the same shard, chosen deterministically from (seed, epoch, index) — and the count never changes. raise is kept for single-device runs and is refused at config load when runtime.strategy names ddp/fsdp/deepspeed.
transform
On a CUDA box the transform stage moves to the far side of the H2D copy, and it is the same function either way — the mel filterbank is moved to its input's device, not the other way round, so the collate and the post-copy hook cannot produce different answers. Two things change when it moves: a worker stops spending its time on FFTs, and what crosses the bus gets smaller — a waveform rather than its spectrogram, and for video a uint8 clip rather than the float32 normalized one, which is 4x. Deferred only when there is a device, the decoder landed on the host, and the preprocessor has declared the work device-agnostic; --no-device-transform pins it back into the collate to compare.
shuffle
block shuffles the shard order, then within each shard, then concatenates — so every read stays inside one already-open shard, which is the entire reason to shard over object storage. A global permutation is a perfect shuffle and one seek per sample; right on local SSD, ruinous over a network. What block costs you is cross-shard mixing within a batch, which is a property of how the corpus was written — fix it at materialization, not by paying for random access every epoch.

The number you want is the rate at which p95 crosses 200 ms, and that is what the ramp is for — a flat load only tells you whether one chosen rate passed. Read it off the k6 output, or off the latency panel in the Grafana ML Framework — Serving dashboard while the ramp climbs.

retrains
This DAG does not choose a model. train fits whatever TRAIN_CONFIG names — no --select, no model.name override. Choosing a family is a decision; retraining it on fresh data is a routine, and they belong on different clocks. The bake-off runs out of band (stage 7) and hands its answer over as a file: 
mlf select -c configs/example_selection.yaml \
           --emit-config configs/winner.yaml     ← commit this

# winner.yaml carries:  model.name · tuned model.params · select.enabled: false
A candidate config is built with the comparison switched off, so the emitted file cannot start another one. That is the whole handoff.
why not daily
Re-running the bake-off nightly does not just spend one tuning budget per candidate on a decision nobody will revisit. When two families sit within noise of each other the winner flips on cross-validation variance — so the family in production changes with no one having chosen it, and the latency budget the HPA was sized for, the explainability story, and on-call's mental model of what is running all change with it.
guard
assert_pinned_config is what makes that structural rather than conventional, and it is not redundant with having no selection stage: mlf train reads select.enabled from the YAML, so a config with the comparison switched on would bake off inside the train task — daily, under one task id, invisible in the graph. The guard runs first, before dvc pull, with retries=0, and names the file and the fix.
fan-out
To distribute a bake-off you do want, mlf select --candidate / --collect fan out across dynamic task mapping — in a separate, occasionally-triggered DAG that ends at collect_winner: 
tune_candidate.expand([xgboost, lightgbm, catboost, mlp])   ← concurrent
    → collect_winner        → selection.json + a proposed winner.yaml
Its output is a pull request, not a deployment: a model-family change deserves a diff and a reviewer, and the retraining DAG picks it up on its next run once merged. Needs Airflow ≥ 2.3 for .expand().
note
The gate fails the run if accuracy is below ACCURACY_GATE; promotion sets the @production alias in MLflow. It runs on a timer, never on an accuracy signal.

No endpoint exposes the live registry version. /health's bundle_version is manifest.bundle_version — a schema number for the bundle layout, constant across every model you will ever train. /metrics' model and backend labels name the family, not the version. How to read this: Stages 0–2 are shared setup. Stages 5–8 are the training path and produce the bundle; stages 9–11 and 15 are the inference path and consume it. They are independent — connected only through the bundle.

Stage 5b is the one branch. Tabular data goes 5 → 8 and never touches it. Anything that has to be decoded — audio, video, images, token shards — goes through mlf materialize first, once per corpus, and every run over that corpus then shares the index. It is numbered 5b rather than 6 precisely because it is a fork rather than a step everyone takes.

Ascending ≠ sequential. Stages 12–14 are numbered in the order you'd first set them up, but they fire on their own triggers afterward: Airflow on a daily timer, CI on push, CD on tag, K8s on a deploy. Only stages 0–11 are a line you type top to bottom.

Every mlf verb enters at src/ml_framework/cli.py — build_parser() (line 544) declares them, main() (line 951) dispatches them, and each branch imports its stage lazily so a torch-free install still starts. Everything else on this page is either a config file some external tool reads (Dockerfile, docker-compose.yml, dvc.yaml, the workflows, the kustomization) or a module with its own __main__ guard (spark_preprocess, contracts, model_quality). Two stages are lettered, not numbered, and both are things you do once. 13b is the first cluster bring-up — the Secret that has to exist before kubectl apply -k deploy, which the apply will not create and will not warn you about. 14b is the way back: a promotion is an MLflow alias and a Kubernetes rollout, so an undo is both, and the question of which model is live has no answer on the serving side at all.
